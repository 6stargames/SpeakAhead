# **Advanced Augmentative and Alternative Communication Systems: Architectural Specifications, Human-Computer Interaction Mechanics, and Clinical Integration**

## **Introduction to the Interface as a Cognitive Prosthesis**

The engineering and design of Augmentative and Alternative Communication (AAC) systems occupy a highly specialized intersection of human-computer interaction (HCI), computational linguistics, motor learning theory, and stringent accessibility standardization. For individuals presenting with complex communication needs—particularly those managing severe motor speech disorders, apraxia, cerebral palsy, or conditions necessitating non-traditional physical access methods—the digital interface transcends standard software utility. It operates as a literal extension of the user’s cognitive and linguistic faculties. Consequently, the architectural framework must inherently prioritize the reduction of cognitive load, the preservation of strict motor planning consistency, and the implementation of fail-safe interaction paradigms that tolerate physical fatigue and intention tremors1.  
The present analysis provides an exhaustive architectural review and rigorous design specification derived from an iterative, human-centered AAC software development cycle. Specifically, this report dissects the transition from a foundational implementation phase ("Round One") to a sophisticated secondary redesign phase ("Round Two"). This secondary phase is necessitated by critical empirical failures observed in live, real-world environments. The subsequent directives address these breakdowns, establish uncompromising accessibility and vocabulary specifications, define immutable technical constraints, and outline a comprehensive developmental roadmap structured across seven priority engineering tasks. The findings synthesized herein function as a definitive, evidence-based blueprint for interaction designers, visual designers, and software engineers tasked with constructing robust, non-reflowing, and highly accessible AAC platforms1.

## **Foundational Architecture: The Round One Implementation**

The initial phase of the AAC system redesign successfully established the baseline visual and interactive architecture of the application. This foundational phase deliberately transitioned the system away from fluid, abstract user interfaces toward a highly structured, standards-compliant ecosystem. The overarching clinical rationale was to optimize the interface for rapid cognitive processing and predictable physical access, prioritizing stability over aesthetic dynamism. The architectural parameters finalized in this phase are classified as immutable baseline constraints for all subsequent developmental iterations1.  
The established paradigms focus heavily on minimizing visual search times and ensuring that physical and optical targets meet, or exceed, stringent accessibility thresholds. The implementation of high-contrast themes and precise programmatic focus management directly addresses the visual and cognitive challenges that frequently co-occur with severe motor impairments.

| Architectural Feature | Technical Specification | HCI and Clinical Rationale |
| :---- | :---- | :---- |
| **Output Ribbon & Speak Action** | Persistent output ribbon with a fixed "Speak" action anchored at the top of the viewport. | Ensures the primary mechanism for vocalizing an utterance remains in a predictable, high-prominence location, eliminating the cognitive overhead of searching for the execution command across varying screen states1. |
| **Quarantined Suggestion Strip** | A fixed-height horizontal strip strictly designated for machine-proposed predictive text and AI tokens. | Segregates human-generated linguistic intent from machine-generated probabilistic suggestions, actively preventing cognitive blending and unpredictable layout shifts during sentence composition1. |
| **Vertical Navigation Spine** | A standardized vertical navigation spine for accessing discrete systemic modules. | Preserves the critical horizontal real estate required for the core vocabulary board while providing a consistent structural anchor for interface navigation1. |
| **Universal Core Board** | A 36-word grid adhering strictly to the Modified Fitzgerald Key for color-coding. | Provides immediate access to high-frequency core vocabulary. The strict part-of-speech color-coding facilitates rapid syntactic assembly and grammar acquisition without requiring explicit literacy1. |
| **Target Sizing and Scaling** | 80px minimum targets on all locked interaction grids. | Aligns with and exceeds WCAG 2.2 Target Size (Minimum) criteria (2.5.8), ensuring reliable activation for users with gross motor instability, spasticity, or intention tremors1. |
| **Programmatic Focus Rings** | WCAG 2.4.13 compliant focus indicators applied globally. | Ensures that users operating via keyboard, mechanical switch, or optical gaze can instantly identify the active element without visual ambiguity1. |
| **High-Contrast Palette** | True yellow-on-black high-contrast visual theme natively supported. | Maximizes visual distinction for users with cortical visual impairment (CVI), ocular motor apraxia, or generalized reduced visual acuity1. |
| **Instant Emergency Phrases** | Pinned, instant-speak emergency phrases (e.g., HELP, PAIN). | Bypasses the standard sentence-building buffer, allowing for immediate, zero-latency vocalization during physiological distress or medical necessity1. |
| **Transcript Demotion** | System transcript relegated to a distinct "Listen" view; digital agent restricted from unprompted speech. | Reduces visual noise on the primary communication surface and ensures the user retains total, autonomous control over the device's acoustic footprint in shared environments1. |
| **Presentation Toggle** | Hardware-accelerated symbol and text-only presentation toggle. | Accommodates longitudinal literacy development, allowing the system to scale fluidly from supporting emergent, symbol-reliant communicators to fully literate adults seeking maximum information density1. |

These structural commitments deliberately reject the prevailing software trend of fluid, responsive web design. The interface was engineered to serve as a reliable linguistic prosthesis, a clinical objective that mandates the total elimination of unpredictable layout behaviors or dynamic DOM reflows.

## **Empirical Failures and Systemic Friction Points**

Despite the theoretical soundness of the foundational architecture, the deployment of the initial redesign into a live, real-world environment surfaced severe interaction flaws. Empirical observations derived from an evening of practical use in a complex auditory environment—specifically, a room containing multiple human speakers and active background audio (a podcast)—highlighted critical breakdowns in the human-machine interaction loop. These failures are documented phenomena that actively impeded communication and generated profound user fatigue1.  
When designing for individuals who may produce language at an average rate of 10 to 15 words per minute, interface inefficiencies do not merely constitute minor usability annoyances; they result in a catastrophic loss of metabolic effort, temporal relevance, and social agency7.

| Documented Failure Mode | Context and Trigger | Impact on the User Experience |
| :---- | :---- | :---- |
| **Absence of Word-Level Deletion** | A user exhibiting a motor tremor double-tapped a target, resulting in the buffer reading I you he it it it. The only available repair mechanism was a global "Clear" function. | **Critical.** Destroying an entire utterance to correct a single terminal error forces the user to rebuild the sentence from nothing. For a user operating at 12 words per minute, this represents an unacceptable loss of energy and time, frequently causing them to abandon the communicative attempt entirely1. |
| **Amputated Suggestion Strip Contents** | The fixed-height suggestion strip successfully prevented board reflow; however, when dictation state and prediction chips co-occurred, the chips rendered half-clipped at the fold. | **Severe.** Users cannot parse or interact with partially rendered UI elements. This forces a visual guessing game and explicitly violates fundamental accessibility principles regarding the absolute visibility of interactive targets1. |
| **Phantom Speaker Attribution** | Pitch separation algorithms misidentified background audio and ambient noise as distinct human speakers (Speakers 2 through 6). The system committed junk micro-turns (e.g., E budding.) as permanent conversational records. | **Moderate to Severe.** The transcript becomes flooded with auditory garbage, rendering it useless for actual conversation review. Furthermore, the tools required to merge or delete these errors were buried in a separate "Settings" view, divorcing the repair action from the context of the error1. |
| **Spoken vs. Unspoken Ambiguity** | Dictated but unspoken turns (words generated in the buffer but never broadcasted via text-to-speech) appeared as full-weight blue bubbles, visually identical to phrases the room actually heard. | **Moderate.** Creates a false historical record of the interaction. The user and their communication partners cannot quickly ascertain which utterances successfully reached the environment versus which were merely drafted and abandoned1. |
| **Unoptimized Board Scaling** | Despite the core board being allocated 75% of the screen real estate, the individual cells remained fixed at their 80px minimum floor, leaving the bottom third of the viewport entirely empty. | **Moderate.** Fails to maximize the physical interaction area. For users with fine motor deficits, larger targets drastically reduce the precision required for selection, thereby increasing communication speed and reducing fatigue. Stopping at the 80px floor unnecessarily penalized users operating on large displays1. |
| **Dangerous Dark Mode Contrast** | The \--danger design token, originally optimized for text resting on dark backgrounds, was erroneously applied as a button fill for emergency actions. This resulted in white text on pale salmon in dark mode. | **Critical.** Emergency actions (HELP, PAIN, CAN'T BREATHE) must mathematically be the most visually salient elements on the interface. Poor contrast under emergency cognitive load delays time-to-activation, actively jeopardizing user safety1. |

These failures mandate a fundamental paradigm shift in how error recovery, spatial constraints, and visual hierarchies are treated in the secondary development phase. Specifically, error recovery must be elevated to a first-class citizen of the interface, equal in spatial prominence and accessibility to initial vocabulary selection.

## **The Seven Priority Development Tasks**

The core objective of the secondary design phase is the systematic resolution of the observed failures, coupled with the implementation of advanced access methods and highly secure vocabulary management tools. The software development process is strictly prioritized into seven interconnected tasks. Interaction models and logical sequences must be robustly argued and clinically justified prior to the drafting of static visual frames, ensuring that the HCI logic is computationally sound before aesthetic layers are applied1.

### **Task 01: Utterance Recovery and Motor-Planned Repair**

The highest systemic priority is the implementation of a precise, word-level backspace directly integrated into the composition buffer. This control must exist as a first-class board element, possessing the same physical dimensions, visual prominence, and fixed spatial positioning as the core vocabulary cells.  
The interaction model must explicitly account for severe motor-planning constraints. If a user relies on a highly automated, deeply ingrained motor sequence to generate language, the mechanism to undo an error must be equally predictable and rapidly reachable via direct touch, switch scanning, and eye-gaze dwell. Furthermore, the concept of "repair" extends into the social dimension of AAC utilization: the system requires a definitive "undo" function for accidental activations of the global "Speak" command. Retracting an utterance socially and digitally is a complex action that must be seamlessly designed into the immediate output ribbon or the primary board layout. Success in this task is strictly defined by the user's ability to resolve a cascading tremor error (e.g., the it it it incident) in exactly two precise mechanical selections, with a physical control placement that is highly defensible to a clinical motor-planning analysis1.

### **Task 02: Spatial Geometry of the Suggestion Strip**

The rigid "no-reflow" architectural constraint dictates that the suggestion strip's height and spatial y-coordinates remain absolutely fixed to prevent the core board from shifting beneath the user's hand or gaze1. The engineering challenge lies entirely within the interior information architecture of this specific strip.  
The interaction designer must construct a rendering logic that elegantly manages spatial collisions between dictation status text, agent-staged speech, and algorithmic predictive text chips. The system requires strict prioritization rules determining what subset of data is scrollable, what is paginated, and what is dynamically culled from the view entirely when pixel limits are reached. Crucially, the UI DOM must enforce a rule where no interactive element is ever rendered partially, clipped mid-pixel, or otherwise amputated. Success in this domain requires the generation of exhaustive visual mockups illustrating every mathematically possible combination of strip contents—including catastrophic text overflow scenarios—demonstrating that all content remains fully legible and interactive without violating the fixed boundaries of the strip1.

### **Task 03: Auditory Processing and Transcript Fidelity**

The cognitive disconnect caused by burying transcript repair tools in the system's Settings menu must be eliminated. The system must permit naming, merging, and claiming voices (the "this is me" function) directly from the transcript label within the active "Listen" view1.  
This task requires the establishment of a rigorous confidence-threshold policy for audio processing, specifically targeting the logic within the src/speech/speakers.ts architecture. The software must programmatically determine at what length or specific confidence interval an environmental sound is classified as a valid conversational turn versus when it is held in a temporary buffer, collapsed, or immediately discarded as junk noise. Furthermore, the visual hierarchy of the transcript must clearly demarcate dictated-but-unspoken text from fully vocalized text. Unspoken drafts must be visually subordinate (e.g., utilizing reduced opacity or outlined bubble styles), allowing users and caregivers to differentiate between internal cognitive composition and externalized speech at a glance. Success is defined by the user's ability to clean up a heavily polluted transcript containing multiple phantom speakers in under sixty seconds without navigating away from the core conversational view1.

### **Task 04: Switch Access and Scanning Architectures**

While the initial DOM was constructed in a logical scan order, the interface lacks the actual scanning engine required for alternative physical access. This task mandates the complete engineering of a robust scanning architecture encompassing the ribbon, suggestion strip, navigation spine, core board, and emergency surfaces1.  
The implementation must support sophisticated row-column scanning, frequently referred to in clinical literature as group-item scanning. In this paradigm, the interface highlights an entire row (or functional group) first; a switch hit accepts that row, and the system subsequently steps through the individual columns within that row until the target is reached7. This architecture heavily reduces the physical effort required to traverse large matrices, as scanning efficiency is measured in "scan steps"—the distance traveled from the upper-left origin to the final target11. Research indicates that placing the most frequently used items in locations with the shortest scan distance significantly enhances the Text Entry Rate (TER)10. The layout efficiency can be mathematically modeled by summing the frequency of an item and multiplying it by its required scan steps11.  
The design must specify exact step timing parameters (scan rates) and support granular user adjustments, as optimal scan rates dictate the overall communication speed10. The system must also accommodate two-switch step scanning. In two-switch scanning, the user hits one switch to manually advance the highlight at their own pace, and a second switch to execute the selection. While this method increases the total volume of physical switch hits, it is cognitively less demanding as it removes the psychological pressure of automated temporal windows, making it suitable for users with high cognitive function but limited motor stamina7.  
Crucially, the system must include a non-negotiable "global interrupt." Regardless of where the scanning loop is currently positioned in the matrix, a specific, deliberate physical action (e.g., a long-press or a rapid double-click of the primary switch) must instantly jump systemic focus to the emergency response surface. Success requires drafting the full logical loop of the scanning model, defining exact temporal sequences, and providing an honest mathematical calculation of switch-hits-per-word for the core vocabulary1.

### **Task 05: Oculomotor Access, Gaze Dwell, and Rest Zones**

For users presenting with profound physical disabilities, such as late-stage Amyotrophic Lateral Sclerosis (ALS), high-level spinal cord injuries, or severe spastic cerebral palsy, optical eye gaze tracking represents the only viable systemic access method. The interface must be fundamentally optimized for optical targeting, explicitly acknowledging the technical reality that the browser will operate via an external eye-tracker acting as an emulated mouse pointer1.  
Dwell selection occurs when a user intentionally maintains their gaze on a specific target for a predetermined temporal threshold, triggering an activation without a physical click1. The UI must feature highly visible, center-out progress indicators (such as a radially filling circle or a shrinking bounding box) to provide continuous visual feedback during the active dwell period. The dwell duration must be highly user-adjustable, specifically within the clinically validated range of 350 to 1000 milliseconds, allowing the system to accommodate both rapid, experienced users and those requiring longer visual processing times1.  
A primary, well-documented failure mode in eye-gaze AAC systems is the "Midas touch" problem, wherein the system erroneously activates every element the user visually inspects while simply reading the board or searching for a concept. To actively mitigate this, the design architecture must incorporate strategically placed "rest zones." These are intentionally inactive geometric areas of the screen where the user's gaze can park indefinitely without triggering any systemic action or feedback loop. Furthermore, target hit-box margins must be mathematically expanded beyond the visible borders of the cell to tolerate the inevitable optical calibration drift inherent to commercial eye-tracking hardware. Success is achieved by specifying dwell feedback to the exact pixel and millisecond and explicitly resolving the Midas-touch dilemma through architectural layout rather than mere documentation1.

### **Task 06: Lexical Architecture and Motor Planning**

Language is deeply personal, and a static, universal core board is entirely insufficient for expansive, individualized communication. This task unifies three intricately linked vocabulary management features that share the primary grid architecture.  
First, the system requires "Fringe folders"—categorized sub-vocabularies containing highly specific nouns such as People, Places, or Food. To prevent users from becoming cognitively lost in complex navigational trees, these folders must be accessible directly from the main navigational spine and strictly limited to a maximum architectural depth of two levels1.  
Second, the system must feature a highly secure caregiver editing flow. Caregivers and speech-language pathologists (SLPs) require the ability to rapidly program new vocabulary in-situ. This editing flow must be heavily sandboxed behind a deliberate unlock mechanism (such as a randomized PIN or an extended touch-hold) and feature an unmistakable visual state that clearly differentiates "editing mode" from "talking mode." As new words are typed into the system, the architecture must automatically apply the Modified Fitzgerald Key color-coding based on the word's syntactic class (e.g., automatically coloring a newly added preposition black, or a verb green), eliminating the need for parents to possess formal linguistic or grammatical knowledge1.  
Third, the design must implement "Progressive Masking." This technique is derived directly from the neurodevelopmental principles popularized by robust AAC systems like LAMP Words for Life (Language Acquisition through Motor Planning)16. The neurological premise of motor planning is that fluent communicators do not communicate by consciously searching for the visual representation of a word; rather, they rely on deeply ingrained, highly automated motor plans—muscle memory orchestrated by the basal ganglia17. In verbal speech, the brain automatically directs the articulators (tongue, lips, jaw) through a highly specific, repeatable physical sequence. In AAC, the finger, switch, or eye acts as the articulator. If an interface dynamically rearranges the position of the word "apple" depending on how many words the user currently knows or which folder they are in, it destroys the motor plan, forcing the user to visually scan the board every single time they wish to speak. This induces massive cognitive fatigue and severely limits communication speed (WPM)8.  
By utilizing progressive masking on a fixed-grid layout, the full grid of vocabulary is programmed and spatially locked from the user's first day of use1. Instead of introducing smaller grids and rearranging icons as the user's vocabulary grows, words are simply hidden (masked) in their permanent physical positions. As the user's communicative competence expands, additional words are unmasked, leaving the fundamental layout entirely unchanged. A beginner utilizing only four visible words is actually navigating the exact same physical geography as the expert utilizing a fully populated 36-word board, merely with 32 cells masked. Success requires a caregiver to be capable of adding a highly specific fringe word (e.g., "my daughter Ellie") in under thirty seconds without breaking the grid structure1.

### **Task 07: Symbol Integration and Psycholinguistic Norms**

The placeholder emojis utilized in the first iteration are wholly inadequate for robust semantic representation (e.g., utilizing a lightning bolt to represent the complex verb "do"). The system must implement the ARASAAC (Aragonese Portal of Augmentative and Alternative Communication) symbol library for all 36 core words and associated fringe vocabulary1.  
ARASAAC symbols, maintained by the Government of Aragón in Spain, exhibit a remarkably high degree of iconicity and transparency, meaning the visual form of the symbol closely and intuitively resembles its intended real-world referent22. This high translucency lowers the cognitive demand required to establish a connection between the graphic and the linguistic concept, making it clinically superior to abstract line art for many users presenting with Level 3 Autism Spectrum Disorder (ASD), cognitive impairments, or severe language delays23. Normative studies on the ARASAAC dataset demonstrate high scores in name agreement, conceptual familiarity, and imageability, which correlate strongly with faster visual processing and vocabulary acquisition25.  
The software engineering for this task requires specifying exactly how the ARASAAC API is bound to specific text inputs, how symbols are fetched over the network, and crucially, how they are cached locally to satisfy the strict offline-availability constraint1. Furthermore, the UI must intelligently adapt when the user toggles to text-only mode, maximizing textual information density once the visual symbols are removed from the DOM.  
Critically, the utilization of ARASAAC symbols introduces strict legal constraints that govern the software architecture. The library is governed by a Creative Commons BY-NC-SA 4.0 license26. The design documentation must explicitly outline how appropriate attribution to Sergio Palao and the Government of Aragón is maintained within the app interface26. Furthermore, the engineering team must assure that the integration complies with the non-commercial (NC) and share-alike (SA) stipulations. This legally prohibits the software from being repurposed as a for-profit commercial product utilizing these specific visual assets, a vital consideration for the open-source nature of the platform28.

## **Anthropometric and Accessibility Standards**

The architectural guidelines impose severe and exacting accessibility requirements that govern color theory, spatial rendering, and complex auditory output. These constraints ensure the application remains operable across a vast spectrum of physical and sensory disabilities.

### **Visual Contrast and Thematic Integrity**

The clinical failure of the dark-mode \--danger token necessitates a complete audit of the application's design tokens. The emergency response surfaces must mathematically represent the highest contrast ratio of any element on the screen, across all themes (light, dark, or high-contrast). The design cannot rely on subjective visual color picking; it must utilize algorithmic contrast measurement to ensure immediate, unmistakable visibility under extreme psychological or physiological stress1.

### **Grid Target Scaling and Focus Management**

While the previous iteration respected the 80px target floor, the interface must now aggressively scale interactive elements to fill the available physical viewport. If a tablet display offers extensive vertical real estate, the core board cells must expand proportionally beyond the 80px minimum to consume the lower third of the screen. Larger physical targets directly correlate with reduced motor-planning time and fewer accidental mis-hits for individuals with dysmetria or intention tremors1. Simultaneously, the focus rings that outline these scaled targets must strictly adhere to WCAG 2.4.13 requirements, ensuring that the stroke width and color contrast of the focus indicator are sufficient to track the user's progress during switch scanning or keyboard navigation1.

### **Auditory Access and W3C ARIA DOM Architecture**

The application must remain fully functional while native operating system screen readers (e.g., Apple VoiceOver, NVDA, Android TalkBack) run concurrently1. This introduces highly complex W3C ARIA (Accessible Rich Internet Applications) engineering challenges. The interface relies on dynamically updating text buffers and AI suggestion strips. If these DOM elements are improperly tagged, the screen reader will continuously interrupt the user's thought process, creating auditory chaos.  
The DOM architecture must carefully distinguish between aria-live="polite" and aria-live="assertive" regions31. As noted in W3C ARIA working group discussions, the misuse of live regions—such as a status updating constantly—creates a hostile auditory environment32. Constant background transcript updates should likely remain polite or be completely suppressed from the screen reader's focus unless specifically queried by the user. Conversely, emergency alerts or critical system state changes must be tagged as assertive to immediately interrupt current speech32. The software must elegantly bridge the gap between visual augmentative communication and auditory feedback without overlapping audio channels or overwhelming the user's auditory processing capabilities.

## **Linguistic Architecture and Vocabulary Specifications**

The layout and presentation of words within the interface are governed by strict neurolinguistic and morphological principles. The design must minimize the cognitive load of syntax generation while strictly preserving the spatial memory of the user.

### **The Modified Fitzgerald Key Contract**

The Modified Fitzgerald Key is a foundational standard in AAC design. It assigns specific background colors to distinct parts of speech to facilitate rapid visual scanning and grammatical sentence construction4. Under this system, vocabulary is generally structured from left to right on the board to mirror standard syntactic structures (e.g., Subject-Verb-Object)4.

| Syntactic Category | Modified Fitzgerald Key Color | Clinical Application |
| :---- | :---- | :---- |
| **People / Pronouns** | Yellow | Placed on the far left to initiate sentences (e.g., I, You, He). |
| **Verbs / Actions** | Green | Centrally located to form the predicate core (e.g., Go, Want, Stop). |
| **Adjectives / Descriptors** | Blue | Grouped to modify nouns (e.g., Good, Bad, Big). |
| **Nouns / Things** | Orange | Placed toward the right to complete Object structures. |
| **Social / Conversational** | Pink / Purple | Used for pragmatic framing (e.g., Please, Hello). |
| **Prepositions / Conjunctions** | Black / White | Used for spatial relations and syntax joining (e.g., In, On, And). |

The second design brief establishes the Fitzgerald Key as an absolute, non-negotiable contract1. Color cannot be used arbitrarily for aesthetic variance; it must strictly convey grammatical class. If a new folder is created or a new scanning highlight is introduced, it must seamlessly extend the existing key without improvising contradictory color schemes. The automated assignment of these colors during the caregiver editing flow is essential to maintain the integrity of the key across the entire application ecosystem1.

## **Hard Technical Constraints and Environmental Limitations**

The design and engineering teams must operate within a rigid framework of technical, ethical, and environmental constraints established during Round One and expanded upon in Round Two1.

> 1. **Total Offline Functionality:** The application must function entirely offline. Individuals in rural areas, institutional settings, or hospitals often lack reliable internet infrastructure. Core text routing, grammar engines, symbol rendering, and text-to-speech processing must execute natively on the local hardware1.  
> 2. **Absolute Data Privacy:** Voice audio recorded by the device microphone for the purpose of transcript separation or environmental processing must never leave the local hardware. Cloud processing of ambient room audio represents a severe breach of user privacy and is strictly forbidden1.  
> 3. **No Unprompted Agent Speech:** The digital agent or device must never vocalize unprompted. The user must maintain total autonomous control over when the device projects acoustic sound into the physical environment1.  
> 4. **Instant Emergency Access:** Emergency communicative actions must always be reachable within a single physical action (e.g., one tap, one global switch interrupt), bypassing any nested folders, menus, or composition buffers1.  
> 5. **The "No-Reflow" Edict:** As dictated by motor-planning science, interactive grids, suggestion strips, and navigation spines must remain absolutely fixed. Any responsive web design technique that shifts, reorders, or dynamically reflows these elements in response to content length or screen orientation is fundamentally incorrect and explicitly prohibited1.  
> 6. **Fitzgerald Key Compliance:** Color denotes grammatical class uniformly across the entire ecosystem without exception1.  
> 7. **Creative Commons Compliance:** The ARASAAC symbol integration must strictly adhere to the BY-NC-SA 4.0 license, barring the software from being repurposed as a commercial product utilizing these specific assets1.

## **Deliverables and Protocol Specifications**

The outputs required from the design and engineering teams extend far beyond standard UI mockups. The deliverables must comprehensively document the temporal, spatial, and logical flow of the system.

* **Philosophical and Technical Rationale:** Before rendering the interface, the designer must formally argue the interaction models governing error repair, alternative access scanning, and the caregiver editing flow1.  
* **Sequential Interaction Flows:** Because dynamic access methods like scanning and oculomotor gaze dwell cannot be evaluated via static frames, the designer must provide sequential flow diagrams. These sequences must illustrate the precise operational loop of the highlight traversing rows and columns, as well as the frame-by-frame visual progression of the dwell-selection indicator1.  
* **Tokens and Millisecond Timings:** The engineering documentation must contain exact, hard-coded values for all interactive mechanics. This includes dwell durations (defined between 350ms and 1000ms), switch scanning step intervals, focus highlight stroke widths and colors, the corrected hex values for the dark-mode \--danger tokens, and the algorithmic rules governing how cells dynamically scale beyond their 80px minimum floor to consume empty viewport space1.  
* **Empirical Test Script Protocol:** The development cycle mandates real-world clinical testing. The designer must draft a comprehensive testing protocol for the next live session. This script must explicitly define what interactions to attempt, the specific quantitative metrics to capture (e.g., selections required per utterance, frequency of errors per utterance, time-to-repair in seconds), and the exact criteria that would clinically or technically falsify the proposed design architecture1.

## **Conclusion**

The architecture of a robust Augmentative and Alternative Communication system requires an uncompromising adherence to clinical research, motor planning theory, and strict accessibility constraints. The exhaustive analysis of the "Round Two" design brief reveals that while foundational layouts successfully stabilized the interface during the initial development phase, the granular realities of real-world use exposed critical friction points in error recovery, spatial management, and auditory processing.  
By systematically addressing the seven priority tasks—ranging from the implementation of word-level repair and precise switch-scanning mechanics to the integration of ARASAAC symbols and LAMP-inspired progressive masking—the resulting software will transition from a functional prototype into a highly reliable, low-fatigue linguistic prosthesis. The strict enforcement of non-reflowing layouts, precise dwell and scan timings, and automated syntactic color-coding ensures that the cognitive and physical burden is shifted away from the user and absorbed entirely by the system's underlying logic. Following this comprehensive specification will yield an AAC ecosystem that honors the metabolic energy of its users, providing rapid, autonomous, and failsafe communication regardless of the individual's physical access method or cognitive profile.
